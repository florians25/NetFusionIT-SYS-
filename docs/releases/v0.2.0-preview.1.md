# NetFusion ERP · v0.2.0-preview.1

Entwicklungs-Preview vom 22.10.2026. Ausschließlich Standardcontrols von OpenUI5 1.153.0 mit Horizon-Theme. Dieser Stand ist keine Produktionsfreigabe und deckt den Masterprompt noch nicht vollständig ab.

## In dieser Preview

- Eigenständiges Service-Cockpit mit echten Kennzahlen, Arbeitsvorräten, Filtern und direkter Technikerzuweisung; separate App-Übersicht.
- Kundenportal → Ticket und eigenständiger Servicefall → Belegfluss → Technikerbearbeitung. Öffentliche Kommentare und geschützte interne Notizen.
- Rollen-/Organisations-/Mandantenschutz, versionsgeschützte Kommandos, Idempotenz, atomare Transaktionen und append-only Audit.
- Kundenstammdaten im Entwurf, Kontakte/Adressen und mehrstufige Vier-Augen-Freigabe mit Definitionssnapshot, Rückfrage und Entscheidungshistorie.
- Servicekalender mit Geschäftszeiten, Feiertagen und Zeitzone; SLA-Policies mit expliziten Fristen/Pausenregeln. Vertraglicher Snapshot am Ticket, Reaktions-/Lösungsfristen und historisierte Fristverletzungen.
- Basis-Serviceverträge und technische Objekte mit Seriennummer, Kundenbezug, Hierarchie und Vertragsdeckung.
- Einsatzplanung als nativer OpenUI5 PlanningCalendar, Techniker-Arbeitszeitmodell, Qualifikationen, Abwesenheiten, Verfügbarkeitsempfehlungen und Einsatzstatus. Parallele Buchungen verhindern Doppelbelegung.
- Fachlicher Zusatzbacklog aus allen drei Nutzeranhängen: Serviceangebote, Serviceaufträge und Rückmeldungen, Auftragsvorlagen/Wartungspläne, In-House Repair sowie erweitertes Service Contract Management.

## Prüfnachweise

TypeScript und offizieller OpenUI5-Build; 41 automatisierte Prüfungen ohne Fehler/Skip, einschließlich echter PostgreSQL-API-Tests, Zeitzonen-/Kalenderfälle und Prüfung der OpenUI5-Vorgaben. Drei Chromium-Prozesse prüfen Ticketbearbeitung, Vier-Augen-Freigabe und Kalender → Vertrag → Objekt → Ticket/SLA → Einsatzplanung. Desktop-/Mobilbilder stammen ausschließlich aus isolierten, über die Business-APIs erzeugten Testdaten. Die Entwicklungsdatenbank erhält keine künstlichen Tickets.

GitHub Actions wiederholt Build, Tests, Browserprozesse und Audit vor dem Anlegen der GitHub-Vorabversion. Ein gepushter Tag allein beweist keinen erfolgreichen Actions-Lauf. Screenshots und Quellarchiv werden erst nach erfolgreichen Prüfungen angehängt. Der Status des Remote-Laufs muss auf GitHub geprüft werden, wenn die API aus der Entwicklungsumgebung nicht erreichbar ist.

## Ausführen

Node.js 24 und PostgreSQL für lokale Entwicklung werden über die vorhandenen Skripte eingerichtet:

```sh
npm ci
npm run build
npm run dev:setup
npm run dev
```

Für den Ubuntu-Docker-Server: `docs/deployment.md`, `.env.example` und `compose.yaml`. Keine Geheimnisse oder Entwicklungszugänge im Archiv. Auf dem Zielserver wurde kein Deployment durchgeführt; Docker-Start, HTTPS, Backup/Restore und Produktionsabnahme sind dort noch nachzuweisen.

## Offener Umfang

Serviceangebote/-aufträge, Zeit-/Materialrückmeldung, Lager, Beschaffung, Faktura/PDF/E-Rechnung, FI/DATEV, Kreditprüfung, erweiterte Vertragsfindung/periodische Abrechnung und Werkstattreparatur sind im Backlog. Sichere Uploads/Virenscan, MFA/OIDC, Delegationen/Betragsgrenzen und weitere Betriebsnachweise sind offen. SLA-Wiedereröffnung nach technischer Lösung benötigt eine explizite Folgeregel; die vorhandene Historie wird nicht zurückgesetzt. Planung hat noch keine Umplanung, Reisezeit-/Routenoptimierung, Materialprüfung oder Offline-Synchronisation. OData ist der dokumentierte lesende V4-Teilumfang.

Laufzeitabhängigkeiten: keine bekannten Audit-Befunde beim lokalen Prüflauf. Entwicklungs-Tooling-Befunde siehe `docs/security.md`.
